## 一、V 组说明 · 分层与边界（⚠️ DDD 是推荐，⛔ 不强制）

> ⛔ **定位**：**DDD / 分层是【推荐做法】，⛔ 不是必须遵守的铁律。**
> 本项目里**只有标了【强制】的条款才必须遵守**（V2 / V3 / V7 / V8），其余是"建议这么做"。
> 项目小、一个人做、逻辑还简单 ⇒ ⭐ **可以不分层**，⛔ 别为了"像大厂"硬拆。

### ⭐⭐ 为什么还是推荐 DDD（讲清好处）

```
① 【改一处不用翻全工程】业务规则集中在规则层 ⇒ 改规则不必去 99 个界面文件里找
② 【能单独测】规则不依赖界面/数据库 ⇒ 可写"只测规则"的自动检查
   （实证：某工程 444 条自检里，结构类断言就是纯规则，不碰界面）
③ 【换皮不换骨】换界面框架 / 换数据库 / 换 AI 供应商，业务逻辑不用重写
④ ⭐【人 + AI 一起做时尤其值钱】边界清楚 ⇒ AI 知道"这行该放哪"，
   ⛔ 不会全堆进界面（实测过：某工程 UI 层一度占 40%）
⑤ 【出错好定位】界面的错 / 规则的错 / 外部世界的错，层次分明
```

### ⚠️ 什么时候**别**上 DDD（⛔ 反对教条）

```
· 一次性脚本 / 小工具（几千行以内）⇒ ⛔ 分四层是自找麻烦
· 一个人做、需求还在剧烈变 ⇒ ⭐ 先单层快跑，等"改起来开始疼了"再分层
· ⛔ 为了"架构好看"加层 ＝ 典型过度设计
```

### ⭐ V 组的落地经验（实测）

```
· 光有"文件夹分层"没用：要看【依赖方向】对不对（谁 using 谁）
  验法：搜"规则层/应用层/基础设施层"里有没有 using 界面框架 ⇒ 必须是 0
· 但"层分对了"也可能【里面是空的】：
  实测某工程 Domain 只占 4%、UI 占 40% ⇒ 层摆着，逻辑还在界面里
· ⭐ 所以判 DDD 做没做，⛔ 不看目录，看两个数：
  ① UI 层行数占比（长期 > 40% ⇒ 该下沉）
  ② 有没有"界面直接 using 基础设施"（越界数 ⇒ 应为 0）
```

## 二、V-B 组说明 · 动态路由架构（⭐ 强烈推荐）

> ⭐ **什么叫动态路由**：**运行时按条件选实现**，⛔ 不是编译时写死"就用这一个"。
> 人话例子：`配置里写 A 就用 A；A 挂了自动退 B；本地能算就不走云`。
> ⚠️ 本组是【推荐】，⛔ 不强制 —— 但**只要有"可换的实现"，就该这么设计**。

### ⭐⭐⭐ 为什么推荐它（讲人话的好处）

```
① 【换供应商不用改业务代码】从 A 家模型换 B 家，只改配置，⛔ 业务一行不动
② 【省钱 / 省算力】⭐"本地能算就别上云"这类策略，只有路由能实现
③ 【降级不崩】A 挂了自动退 B，用户无感；⛔ 而不是直接报错
④ 【A/B 对比与灰度】同一件事两条路跑，比一比再定
⑤ 【按环境自适应】家里电脑 / 客户电脑 / 没网，各走不同的路
```

### ⭐⭐ 什么时候该用（判据）

```
✅ 该用：有 ≥2 个"可以互相替代"的实现
        （多家 AI 模型 / 云 vs 本地 / 多个数据源 / 多个渲染器 / 多种存储）
✅ 该用：有"先试便宜的，不行再上贵的"这类成本策略
⛔ 别用：只有一种实现（那就是过度设计，多一层没意义）
```

### ⭐ V-B 组的落地经验（实测）

```
· 路由的"决策"和"实现"必须分开：
  决策（谁被选中）＝ 一处；实现 ＝ 各自独立
· ⭐ 必须有"当前走了哪条"的可见性：
  ⛔ 否则出怪问题时分不清是"路由选错"还是"实现坏了"
· ⭐ 一个总开关把路由关掉（退回单一路径）能极大加速排查
· ⚠️ 降级一定要留痕：⛔ 静默降级 = 用户以为走了 A，其实早退到 B 了
```

## 三、X 组说明 · 业务架构（主系统 → 中控 → 功能模块）

> ⭐ **三层各管什么**（人话）：
> **主系统（魂）**＝"我是谁、我记得什么、我跟你的关系、我允不允许做"；
> **中控**＝"这件事该谁去做、走哪条路、做完记一笔"；
> **功能模块**＝"具体怎么干"。

### ⭐⭐ 为什么推荐这条（好处）

```
① 【加功能不用改主系统】新模块只要"报上名来"（写清能干什么），中控就能调它
② ⭐【魂不会被功能污染】魂只管身份/记忆/关系/授权 ⇒ 换功能不动魂
③ 【调度可换】想把"谁先谁后"改掉，只动中控，⛔ 模块不用重写
④ 【出错好定位】是"没选对模块"（中控）还是"模块自己坏了"（模块）一目了然
⑤ ⭐【能按能力调度】中控按模块"自述"选，⛔ 不用写死 if-else 长链
```

### ⚠️ 什么时候只做两层

```
· 模块少于 ~5 个、且没有"按能力选"的需求 ⇒ ⭐ 魂 + 模块 两层就够
· ⛔ 不许为了凑三层，加一个什么都不干的空壳中控（那就是过度设计）
```

### ⭐ X 组的落地经验（实测）

```
· 判"谁在兼职中控"的机械指标（实测有效）：
  ① 行数异常大的类（某工程 1786 行的类事实上在兼职中控）
  ② 被很多地方调用、自己也调用很多地方的类 = 事实上的枢纽
· ⭐ 判"模块能不能被调度"：看它有没有【自述】（能干什么 / 输入什么 / 失败什么样）
  ⛔ 没自述 ⇒ 中控只能写死 if-else ⇒ 加一个模块要改中控
· ⚠️ 魂的边界最容易破：功能代码一顺手就往魂里塞（"反正她要用"）
  验法：搜魂那个类里有没有"具体业务"的调用 ⇒ 应该只有"身份/记忆/关系/授权"
```
